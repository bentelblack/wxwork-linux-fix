# 01 问题原因

## 当前方案的结论与证据边界

2026-11-09 在 Debian 13 + GNOME / Wayland 上，以官方 deepin-Wine 10.14deepin14、官方企业微信 5.0.10 容器为基座安装腾讯企业微信 5.0.13.6005，做了单变量对照：

| 对照 | 群公告结果 |
|---|---|
| 官方容器和启动环境保持原样 | 异常 |
| 仅在 Wine 引擎的 `lib/wine/i386-windows/kernelbase.dll` 换成官方企微包配套版本 | 正常 |

进程映射和哈希确认实际加载了修改后的模块。该测试保留官方 `files/dlls/`、`WINEPREDLL`、容器注册表、运行库和图形探测逻辑；“仅替换一个模块”仅指 Wine 引擎目录相对配套原版的差异，不是删掉其他官方预加载模块。

本次日志没有复现历史 `CreateWindowEx Error = 1400`。新组合证实的是单模块变化与群公告恢复之间的对照结果；尚未逆向到 `kernelbase` 内具体函数或更底层调用原因。不要把历史错误码直接写成本轮复现证据。

## 历史白屏证据

旧版本中，`WXWorkWeb.exe` 的 CEF 日志出现过：

```text
window_impl.cc(249) Failed to CreateWindowEx ... Error = 1400
web_quality_detector ... white_rate:100
```

Crashpad 转储也显示 CEF 子进程反复崩溃。该组证据说明当时窗口创建失败并伴随白屏，但不能替代当前版本的单变量验证。

早期分析发现，deepin 企业微信包在 `files/dlls/` 中附带定制 Wine 模块；旧启动方式通过 `WINEPREDLL` 预加载它们，并不等价于引擎目录中的模块均被替换。分段对照及后续 deepin-Wine 10.14deepin14 测试把群公告恢复定位到 i386 定制 `kernelbase.dll`。`user32`、`win32u`、`winex11` 等单独加入引擎不足以恢复群公告。不要因此停用官方预加载环境。

## 内置更新的历史问题

早期使用定制 i386 `kernelbase.dll` 时，更新日志记录过本地临时文件创建失败：

```text
[DownloadUpdatePackageTask] open fail (22): Invalid argument
```

`open fail (22)` 对应本地创建 `.Update.tmp` 时出现 `EINVAL`，网络下载尚未开始。`2148081673`（`0x80092009`，`CRYPT_E_NO_MATCH`）是签名检查中的日志，不是下载失败根因。使用原版 i386 `kernelbase` 的历史对照中，更新可以继续下载并启动安装。

这个 EINVAL 结论来自历史测试。新组合仍使用定制 i386 `kernelbase`，因此日常模式的更新风险是推测，不是新版本在线更新测试结论；项目保留原版引擎的更新兼容入口。

## 字体

测试容器已有 `HKCU\\Software\\Wine\\Fonts\\Replacements` 替换规则，但 Windows 字体目录缺少 `wqy-microhei.ttc`，宿主 `fc-match` 也曾回退到 Noto。规则存在不代表目标字体可用。构建脚本从 Debian 官方字体包提取字体、复制入容器并导入字体登记；文件和登记可以自动检查，实际视觉效果仍要在桌面重启后确认。

## 诊断原则

1. 先区分窗口创建、CEF 崩溃和渲染器初始化证据；`ANGLE ... No available renderers` 或 GDI 设置不能单独证明白屏根因。
2. 每轮实验只改变一个变量，并记录启动时间、日志与配置。
3. 用 `/proc/<pid>/maps`、文件哈希确认进程实际加载的模块，不以磁盘位置代替运行时证据。
4. 解密主日志后按操作时间检查；下载窗口关闭可主动取消下载，不能仅凭未完成的文件大小判定下载器故障。
5. 构建模板必须从未登录的官方材料生成，不能带入测试账号数据。
